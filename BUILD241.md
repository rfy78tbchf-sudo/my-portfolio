# Build241 — realized sales use verified broker trade dates

Problem: the period-P&L RPC already matches domestic ledger entries to SSQM2442 trade-day evidence, but realized sales still select and replay those entries using settlement/ledger dates when order_at is absent. A sale from before the selected week can appear in that week as uncalculated; unrelated trade days can also appear to be a same-day buy/sell pair.

Change: reuse the existing individually unique and grouped unique matcher inside get_live_realized_sales, once per call, before security selection and moving-average replay. Only recovered dates enter a small in-memory map. Stored transactions, amounts, fees, costs, holdings, FX, account ownership, privileges and true same-day uncertainty stay unchanged. No new UI or data-collection request. Existing explicit order timestamps take priority. Source matching requires account, domestic currency, API source, ISIN, side, quantity, gross amount, price, source date and unique evidence use; group matching preserves the existing cross-group ambiguity guards. No guessed trading-day subtraction.

Validation: tests/build241_realized_dates.mjs runs the actual RPC in isolated PGlite Postgres with synthetic tables only. It reproduces incorrect period inclusion and false mixed-day cost blocking before the change, verifies the correction, and checks monthly/year boundaries, no ledger mutation, genuine unknown order, mismatched/duplicate/foreign evidence, caller isolation, USD/FX/pending-sale equality. It also executes the existing 42-row grouped-date guard corpus. Browser tests consume synthetic results produced by the SQL test, covering current-period removal, known amount, retained unknown, touch disclosure, amount geometry and 390/402/430px at 100/125%, Chromium and WebKit. Existing full CI remains required.

Performance tradeoff: five alternating runs per version after one warm-up each, same isolated PGlite 0.3.14 / Node24.22.1, 400 synthetic trades and 200 domestic reports, no network or browser. Baseline median68.1ms (66.7–79.8), corrected197.2ms (189.2–206.3). Added evidence matching costs about129ms in this unindexed synthetic database. This is a correctness fix, not a speed improvement or an operating-server/iPhone latency claim. Samples before=[68.1,79.8,67.1,69.5,66.7],after=[206.3,189.2,191.4,200,197.2]. Existing SQL limits remain20s; production read-only check and browser/CI regression are release gates.
